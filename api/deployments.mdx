The Deployments API lets you publish your documentation and track the progress of every release. When you trigger a deployment, InkLoom builds your pages from saved MDX content and pushes them to your hosted site. Each deployment moves through a lifecycle — from `pending` through `building` and `deploying`, before reaching a terminal state of `live` or `failed`. Use the status endpoint to poll for completion and integrate deployments into your CI/CD pipeline.

---

## The deployment object

<ResponseField name="id" type="string">
  Unique identifier for the deployment, prefixed with `dep_`. For example, `dep_7f3k9x`.
</ResponseField>

<ResponseField name="project_id" type="string">
  The ID of the project this deployment belongs to.
</ResponseField>

<ResponseField name="status" type="string">
  The current lifecycle stage of the deployment. Possible values:

  <Expandable title="Status values">
    <ResponseField name="pending" type="string">
      The deployment has been queued and is waiting for a build worker to pick it up.
    </ResponseField>
    <ResponseField name="building" type="string">
      InkLoom is compiling your MDX pages and generating the static output.
    </ResponseField>
    <ResponseField name="deploying" type="string">
      The built output is being pushed to the CDN and DNS is being updated.
    </ResponseField>
    <ResponseField name="live" type="string">
      The deployment completed successfully and is now serving traffic at the deployment URL.
    </ResponseField>
    <ResponseField name="failed" type="string">
      The deployment did not complete. Check your page content for MDX errors and retry.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="environment" type="string">
  The target environment. Either `"production"` or `"preview"`.
</ResponseField>

<ResponseField name="url" type="string">
  The URL where this deployment is (or will be) accessible once live. For production deployments this matches your project's primary URL. Preview deployments receive a unique URL.
</ResponseField>

<ResponseField name="created_at" type="string">
  ISO 8601 timestamp of when the deployment was triggered.
</ResponseField>

<ResponseField name="completed_at" type="string | null">
  ISO 8601 timestamp of when the deployment reached a terminal state (`"live"` or `"failed"`). Returns `null` while the deployment is still in progress.
</ResponseField>

## Trigger a deployment

`POST /projects/:id/deployments`

Start a new deployment for a project. InkLoom snapshots all current saved pages and begins the build process. The response returns immediately with a `pending` deployment object — use the [Get deployment status](#get-deployment-status) endpoint to follow progress.

```bash
curl -X POST https://api.inkloom.io/v1/projects/proj_abc123/deployments \
  -H "Authorization: Bearer ik_live_xxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{"environment": "production"}'
```

### Path parameters

<ParamField path="id" type="string" required>
  The ID of the project to deploy.
</ParamField>

### Request body

<ParamField body="environment" type="string" required>
  The target environment for the deployment. Pass `"production"` to update your live docs site, or `"preview"` to publish to a temporary URL for review. Preview deployments do not affect the production site.
</ParamField>

### Response

Returns the new deployment object with HTTP `201 Created`. The initial `status` is always `"pending"`.

```json
{
  "id": "dep_7f3k9x",
  "project_id": "proj_abc123",
  "status": "pending",
  "environment": "production",
  "url": "https://my-docs.inkloom.dev",
  "created_at": "2025-06-01T14:22:00Z",
  "completed_at": null
}
```

<Tip>
  Use `"preview"` deployments to validate content changes before promoting them to production. Each preview gets a unique URL you can share for review or QA without touching your live site.
</Tip>

## List deployments

`GET /projects/:id/deployments`

Retrieve a paginated list of all deployments for a project, ordered by `created_at` descending.

```bash
curl https://api.inkloom.io/v1/projects/proj_abc123/deployments \
  -H "Authorization: Bearer ik_live_xxxxxxxxxxxx"
```

### Path parameters

<ParamField path="id" type="string" required>
  The ID of the project whose deployments you want to list.
</ParamField>

### Response

```json
{
  "data": [
    {
      "id": "dep_7f3k9x",
      "project_id": "proj_abc123",
      "status": "live",
      "environment": "production",
      "url": "https://my-docs.inkloom.dev",
      "created_at": "2025-06-01T14:22:00Z",
      "completed_at": "2025-06-01T14:23:47Z"
    }
  ],
  "next_cursor": null,
  "has_more": false
}
```

<ResponseField name="data" type="Deployment[]">
  Array of deployment objects for the current page.
</ResponseField>

<ResponseField name="next_cursor" type="string | null">
  Opaque cursor for the next page. Pass as the `cursor` query parameter to continue paginating. Returns `null` on the last page.
</ResponseField>

<ResponseField name="has_more" type="boolean">
  `true` when more deployments exist beyond the current page.
</ResponseField>

## Get deployment status

`GET /projects/:id/deployments/:depId`

Fetch a single deployment by ID to check its current status and metadata. Poll this endpoint after triggering a deployment to track it through to completion.

```bash
curl https://api.inkloom.io/v1/projects/proj_abc123/deployments/dep_7f3k9x \
  -H "Authorization: Bearer ik_live_xxxxxxxxxxxx"
```

### Path parameters

<ParamField path="id" type="string" required>
  The ID of the project that owns the deployment.
</ParamField>

<ParamField path="depId" type="string" required>
  The ID of the deployment to retrieve. For example, `dep_7f3k9x`.
</ParamField>

### Response

Returns the deployment object with its current `status`. Once the deployment finishes, `completed_at` is populated and `status` is either `"live"` or `"failed"`.

## Polling for completion

After triggering a deployment, call `GET /projects/:id/deployments/:depId` on a loop until `status` reaches a terminal value (`"live"` or `"failed"`). Typical deployments complete within 30–90 seconds.

The following shell script polls every 5 seconds and exits when the deployment settles:

```bash
DEP_ID="dep_7f3k9x"
PROJECT_ID="proj_abc123"
TOKEN="ik_live_xxxxxxxxxxxx"

while true; do
  RESPONSE=$(curl -s \
    "https://api.inkloom.io/v1/projects/$PROJECT_ID/deployments/$DEP_ID" \
    -H "Authorization: Bearer $TOKEN")

  STATUS=$(echo "$RESPONSE" | grep -o '"status":"[^"]*"' | cut -d'"' -f4)
  echo "Current status: $STATUS"

  if [ "$STATUS" = "live" ]; then
    echo "✅ Deployment is live!"
    break
  elif [ "$STATUS" = "failed" ]; then
    echo "❌ Deployment failed. Check your page content for errors."
    exit 1
  fi

  sleep 5
done
```

Here is the same logic in Node.js for use in a CI script or deployment pipeline:

```javascript
async function waitForDeployment(projectId, depId, token) {
  const url = `https://api.inkloom.io/v1/projects/${projectId}/deployments/${depId}`;
  const headers = { Authorization: `Bearer ${token}` };

  while (true) {
    const res = await fetch(url, { headers });
    const deployment = await res.json();

    console.log(`Deployment status: ${deployment.status}`);

    if (deployment.status === "live") {
      console.log(`✅ Live at: ${deployment.url}`);
      return deployment;
    }

    if (deployment.status === "failed") {
      throw new Error("Deployment failed. Review your page content and retry.");
    }

    // Wait 5 seconds before the next poll
    await new Promise((resolve) => setTimeout(resolve, 5000));
  }
}

// Usage
waitForDeployment("proj_abc123", "dep_7f3k9x", "ik_live_xxxxxxxxxxxx");
```

<Note>
  Poll at most once every 5 seconds to stay within InkLoom's rate limits. Polling more aggressively will not speed up your deployment and may result in `429 Too Many Requests` responses.
</Note>

<Warning>
  Always handle the `"failed"` status explicitly in your polling logic. A deployment can fail due to invalid MDX in a page, a slug conflict, or an internal build error. When a failure occurs, the `status` field will read `"failed"` and `completed_at` will be set — but the previous live deployment will remain in place and continue serving traffic.
</Warning>
